# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow

- Never commit directly to `main`. Before starting any work, create a new branch off `main` (branch off the latest `main`, not an existing feature branch).
- Before committing, always update documentation affected by the change — `CLAUDE.md` (Status, and whichever topical section covers what changed), `README.md`, and `docs/API.md` if the change alters mandated behavior. Check each for now-stale claims (a feature described as "not built yet" that this change built, a route/shape that changed, a screen that didn't exist before) and fix them in the same commit as the code, not a follow-up. Do this as a deliberate last step prior to committing, not opportunistically while coding.
- When the work is done, commit the changes and push the branch to the remote.
- **Commit message subject line must be a short title, not a sentence** — aim for well under 72 characters, put the "why"/detail in the body after a blank line. GitHub's "Create pull request" form auto-fills the PR title and description directly from a single-commit branch's commit message; if the subject line runs long, GitHub splits it at an arbitrary character count instead of a word/sentence boundary, so the tail of the title spills into the top of the description looking broken (this happened for real — see the `chore/gh-cli-release-workflow-1.0.1` PR). A short subject + a real body paragraph is what makes the auto-filled title and description look intentional rather than truncated.
- Use the `gh` CLI for all GitHub operations (issues, PR status/checks, viewing existing issues to avoid duplicates, etc.) rather than asking the user to do it manually or guessing at web URLs.
- **After pushing, open the PR yourself** via `gh pr create --title ... --body ...` (a real title and body passed as flags, not left for GitHub's commit-message autofill — see the commit-message hygiene rule above for why that autofill can look broken anyway). Then watch for the CI check with `gh pr checks --watch` (or `gh run watch`) and report back the PR link plus pass/fail once it resolves. **Merging stays manual** — never merge the PR yourself, only open it and report status; the user reviews and merges in the GitHub UI.
- CI (`.github/workflows/ci.yml`) runs lint/typecheck/test/build on every PR and push to `main` — treat a red check the same as a local test failure, don't push past it.
- **Since 1.0.0, every PR merged into `main` gets its own release**: bump semver, build/tag/push the container, and tag the release in git, per "Publishing a release image" under Releasing below. This is now a default part of finishing a change, not a separate step the user needs to request — proceed with the release once you've confirmed the PR is merged (still never merge the PR yourself). The only judgment call left to make per release is the *size* of the bump (patch/minor default, major only on explicit instruction — see below).
- **Any non-dev container build (i.e. a build meant to be published, not a local `localscore:local` verification build) MUST be tagged, pushed, and verified per "Publishing a release image" below** — never `podman push` an ad-hoc/untagged image or push only `latest`.

## Issue intake and triage

When the user hands over a batch of issues (bug reports, feature requests, feedback) rather than a single task, don't start coding immediately. Work in two passes:

1. **Assess and group.** Read the full list before filing anything. Issues that share a root cause, code path, or feature area become **one** GitHub issue (body enumerates each original report as a sub-bullet so nothing gets silently dropped); issues that are genuinely unrelated stay separate. Check `gh issue list` first so a resubmitted or overlapping report doesn't create a duplicate.
2. **File via `gh issue create`** (title + body, labels where it helps) for each resulting issue — grouped or standalone. Present the user the final list of filed issues (with numbers/links) and stop there.

Filing an issue is not authorization to work on it — wait for the user to say which filed issue(s) to pick up next, same as any other task.

## What this project is

localscore turns a CVSS base score into the score that actually applies to a specific environment. A vulnerability scanner reports a 10.0; CVSS environmental metrics can correct that for systems that aren't worst-case, but the official FIRST calculators are expert-facing. localscore asks ~12 plain-English questions about a "location" (e.g. "My Data Center", "Retail Kiosks") and derives CVSS environmental metric profiles from the answers, then applies those profiles to any pasted CVSS vector or looked-up CVE.

Self-hosted single container, SQLite on a volume, no accounts, no cloud dependency except an optional NVD CVE lookup.

The product works end-to-end: an npm-workspaces monorepo (`server/` = Hono + better-sqlite3 API, `web/` = React + Vite frontend), the full interview catalog, environment CRUD with answer-derivation, a working scoring engine, a real frontend (environments list → interview wizard → results screen with both a paste-a-vector flow and a CVE-lookup flow, plus a saved-vulnerabilities list with search/filter), NVD CVE lookup, and saved-vulnerability CRUD. No stubbed API routes and no unbuilt UI surface for any of the above.

## Mandated tech stack

- **Runtime**: Node 22 LTS, TypeScript everywhere, strict mode.
- **Backend**: Hono (Fastify only if Hono proves awkward) serving both the JSON API and the built frontend static assets from one process on one port (default 8080).
- **Frontend**: React + Vite, built to static assets at image build time. Plain CSS (custom properties for theming) or a tiny utility layer — no heavy UI framework, no large-runtime component library. Use the `frontend-design` skill for any UI/visual work — see "Frontend design" under Frontend below.
- **Database**: SQLite via `better-sqlite3`, single file at `/data/localscore.db`, WAL mode. Migrations are sequential numbered SQL files (`migrations/0001_*.sql`, …) applied at startup inside a transaction, tracked in a `schema_migrations` table.
- **Scoring**: MUST match FIRST's reference calculators exactly (v4.0 and v3.1). Use an existing maintained library (`ae-cvss-calculator` is the leading candidate) or vendor FIRST's reference code, validated against reference test vectors before committing. Hand-rolled scoring math without reference-validated test vectors is explicitly not acceptable.
- **Testing**: Vitest. Tests are a release gate, enforced both locally and by CI.
- **Container**: multi-stage Dockerfile (plain OCI — builds and runs under Docker or Podman), non-root user, `node:22-slim`/alpine runtime, final image < 300 MB, `HEALTHCHECK` on `/api/health`. The maintainer runs Podman day-to-day, so use `podman`/`podman compose` in docs and examples.

No external services, no telemetry. The only outbound network call anywhere in the app is the optional NVD CVE lookup.

## Architecture

The core design tension the whole app is built around: **environments store raw interview answers, not derived metrics, as the source of truth.** `environment_answers` (question_id + option_id pairs) is authoritative; `environment_metrics` is a materialized cache re-derived from those answers on every save. This is what lets the question catalog evolve over time (`CATALOG_VERSION`) and lets a completed interview be re-opened with prior answers pre-selected without losing data. Never treat `environment_metrics` as something to hand-edit directly — it's always regenerated from answers + catalog in code.

The **question catalog lives in code** (a versioned TS module, `server/src/catalog/catalog.ts`), not in the database. Each answer option emits zero or more `MetricEffect`s tagged with an `effect` of `override` or `cap`:

- **`override`**: unconditionally replaces the base metric (used for environment facts like CR/IR/AR, or MVC:N when a location genuinely holds nothing confidential). Can legitimately raise a score above base — this is intentional for the "blast radius" (Q8) and "safety" (Q9) questions.
- **`cap`**: only applies if it makes the metric *less* severe than the base vector's value, using the severity orderings in `server/src/scoring/orderings.ts`. Never raises severity.

Conflict rule when two questions touch the same metric: later question's `override` wins; a `cap` never displaces an existing `override`. The concrete case baked into the catalog: Q9 Safety's MSI/MSA override always wins over Q8 blast-radius for those same metrics.

**Supplemental metrics (v4.0 S, R, V, RE)** are collected and stored per-environment but are strictly display-only — they MUST NOT affect any computed score (per the CVSS v4.0 specification's own §6). **AU, U (provider-assigned) and threat/temporal metrics (E, RL, RC)** are the opposite: never interviewed, per-vulnerability not per-environment, displayed/scored only from what's pasted in.

Scoring flow: parse the pasted vector → detect version (v4.0 / v3.1 / v3.0-scored-as-3.1-with-a-disclosed-note / v2-rejected) → for each environment with a completed interview for that version, apply stored effects (override then cap-if-less-severe) on top of the base vector → compute with version-appropriate reference math → render one row per environment sorted by modified score descending, each expandable into a plain-English "why" panel (question/answer text, not raw metric codes, with codes in fine print).

An environment with zero answers MUST reproduce the base score exactly — this is both a core design invariant and a required test (`server/test/scoring.test.ts`).

## Domain rules for the scoring code

- CVSS v3.0 vectors are scored using v3.1 equations against the v3.1 profile, with a UI-visible disclosure — never silent.
- v2.0 vectors (including bare `AV:N/AC:L/Au:N/...` syntax) get a friendly "not supported yet" rejection, not an attempted parse.
- If a pasted vector already contains environmental metrics, the environment profile's values win for metrics the profile defines; the vector's environmental values fill in the rest. UI should warn when this happens.
- Full metric-to-question mapping lives in `server/src/catalog/catalog.ts`'s `MetricEffect` wiring per question — consult it rather than re-deriving which question feeds which metric.
- The worked example (base `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` = 9.8, "Disposable Dev Lab" profile → 0.0) MUST exist as an exact-match test case.

## API surface

All JSON under `/api`, no auth, errors as `{ error: string }` with correct status codes. Frontend is served for all non-`/api` paths (SPA fallback to `index.html`) from the same process/port. ## Backend

### Scoring engine

Built on `ae-cvss-calculator` (metaeffekt, Apache-2.0, zero runtime deps, covers CVSS 2.0/3.0/3.1/4.0) — reproduces the worked example (base `9.8` → environmental `0.0`) and known reference vectors exactly; see `server/test/scoring.test.ts`. It's a CommonJS package under `"type": "module"` — import it with `import pkg from "ae-cvss-calculator"; const { Cvss3P1, Cvss4P0 } = pkg;`, not named imports (TS's `NodeNext` resolution will reject named imports from a CJS package).

- `server/src/scoring/parse.ts` — version detection/routing and friendly parse errors. Note: `AV:X` is *not* an invalid value — `X` is the real "Not Defined" enum member shared by every metric — so it's caught separately as "missing required base metrics" via `isBaseFullyDefined()`, not as an unknown-value error.
- `server/src/scoring/orderings.ts` — the cap severity orderings (only the exploitability metrics that ever carry a `cap` effect: AV/AC/AT/PR/UI), and `baseCounterpartMetric()` (strip a leading `M` — works uniformly for every M-prefixed metric, cap or override; CR/IR/AR and the v4 supplemental metrics have no base counterpart).
- `server/src/scoring/index.ts` — `applyEnvironment()` (mutates a parsed vector per override/cap rules; also tracks a running score across the mutation loop so each returned `AppliedChange` carries a real `impact` — the score movement caused by that change on top of everything already applied before it — and a `direction` derived from `impact`'s sign) and `scoreForEnvironment()` (parse + apply + compute in one call).
- `server/src/catalog/derive.ts` — `DerivedMetric` carries `questionId`/`optionId` provenance (used for change explanations), in addition to what's persisted to `environment_metrics`.
- `POST /api/score` recomputes each environment's derived metrics fresh from `environment_answers` at request time rather than reading the persisted `environment_metrics` cache — simpler and self-consistent, at negligible cost (12 questions).
- `Question` (`server/src/catalog/types.ts`) has an optional `finePrint` field for "what this maps to" disclosures on Q1 (reachability→MAV:A is an approximation, not literal CVSS Adjacent) and Q4 (CVSS has no "interaction impossible" value, so the cap only reduces to the hardest interaction level). `InterviewPage.tsx` surfaces it via the question-help modal rather than inline, so it stays out of the way for non-expert users until they ask for it.

### NVD lookup & saved vulnerabilities

- `server/src/lib/nvd.ts` — fetches `services.nvd.nist.gov`, throttled module-wide (~1 req/6s unauthenticated, faster with `NVD_API_KEY`) since NVD's unauthenticated rate limit is shared across all callers in the process, not per-request. `extractVectorOptions()` parses every `cvssMetricV40`/`V31`/`V30` entry NVD returns (deliberately skips `cvssMetricV2` — v2 isn't a supported score) so the UI can show all disagreeing sources; `pickPrimaryVector()` picks the highest-version/Primary-sourced one as the default.
- `GET /api/cve/:cveId` (`server/src/routes/cve.ts`) is cache-first against the `vulnerabilities` table (same table doubles as the NVD cache and the saved-vulnerability list) — a cached CVE is served with no network call unless `?refresh=1`. A failed refresh falls back to serving the stale cache rather than erroring.
- The cache/saved-list dual use is disambiguated by a `saved INTEGER` column (migration `0002_vulnerabilities_saved_flag.sql`): lookups write/update rows with `saved = 0` and never flip an existing row's flag; `GET /api/vulnerabilities` only returns `saved = 1` rows. This closed an early bug where a lookup-then-save produced two list entries.
- `server/src/routes/vulnerabilities.ts` always re-parses and re-scores the vector server-side on save (`parseBaseVector` + `computeScore`) rather than trusting a client-supplied score — consistent with treating derived values as recomputed, not client state, elsewhere in the app. Saving is an **upsert**, not an insert: matched by `cve_id` for NVD-sourced saves or by normalized `vector` for pasted-vector saves, reusing an existing cache row (`saved = 0 → 1`) or an already-saved row in place rather than creating a duplicate. The response's `overwritten` flag distinguishes "this updated an already-saved entry" (`200`) from a first save, including one that reused a cache row (`201`).
- **NVD carry-through works as a side effect of the upsert, not a separate fix**: the POST upsert's `UPDATE ... nvd_json = COALESCE(?, nvd_json)` means that when a save matches an existing cache row by `cve_id` (the normal CVE-lookup-then-save path), it keeps that row's already-populated `nvd_json` even though the client never sends one — the client genuinely never sends `nvdJson` today, and it doesn't need to. Locked in with a mocked-fetch regression test (`server/test/vulnerabilities-route.test.ts`, "NVD data carries through on save").
- Tests mock global `fetch` via `vi.stubGlobal` (`server/test/cve-route.test.ts`); the throttle's module-level `lastRequestAt` needed a test-only reset hook (`__resetNvdThrottleForTests`) since otherwise it bleeds across unrelated test cases sharing the same process and causes spurious 5s+ timeouts.
- `GET /api/major-cves` (`server/src/routes/major-cves.ts`) — a *distinct* path from `/api/cve/:cveId`, deliberately not routed through it. `fetchMajorCves()` (`nvd.ts`) runs two separate NVD searches (`cvssV3Severity=CRITICAL` and `cvssV4Severity=CRITICAL`, both over a 30-day `pubStartDate`/`pubEndDate` window) since NVD's search API has no OR-across-severity-fields query — results are merged by `cveId` (deduping a CVE that's critical under both v3 and v4, preferring the v4.0 entry via the existing `pickPrimaryVector()`), sorted by score desc / most-recent-published as tiebreak, and clamped to 10. Cached in a single-row `major_cves_cache` table (migration `0003_major_cves_cache.sql`) with a `fetched_at`; the route serves the cache unconditionally while it's <24h old, refreshes lazily on access when stale, and falls back to serving the stale cache (with its `fetched_at` disclosed) if the refresh fails — same offline philosophy as the per-CVE cache. No scheduler; refresh is purely access-driven.
- Because it makes two throttled NVD calls per request (each serialized ~6s apart unauthenticated, per the shared module-level throttle), `server/test/major-cves-route.test.ts`'s tests that exercise the real fetch path take ~6s each — `server/vitest.config.ts` sets `testTimeout: 15000` project-wide to cover this (the default 5s isn't enough).
- `extractCveDetails()` (`server/src/lib/nvd.ts`, sibling to `extractVectorOptions`) derives `{ description, published, lastModified, references[], affectedProducts }` from an already-cached `nvd_json` blob at read time — no migration, no stored columns. `description` picks the `lang: "en"` entry (falls back to the first). `references` preserve NVD's tags and are capped at 20, with `Patch`/`Vendor Advisory`-tagged entries sorted first. `affectedProducts` is a best-effort `vendor product` pair parsed from each CPE 2.3 URI's 4th/5th colon-separated fields, deduped, capped at 15 with a `+N more` remainder count — explicitly *not* a version-accurate applicability check, just orientation. Every field tolerates malformed/absent input rather than throwing (`server/test/nvd-details.test.ts`). `GET /api/cve/:cveId` and `GET /api/vulnerabilities/:id` both carry a `details` field (`null` for a pasted-vector save, since those have no `nvd_json`).
- `POST /api/vulnerabilities` prefills an NVD-sourced save's (`cveId` set) `description` from `extractCveDetails()`'s English description, using the row's effective `nvd_json` *after* the COALESCE carry-through above — so the normal lookup-then-save path (which always has `nvd_json` cached) picks it up with no client change. Only fires when `description` is otherwise empty (never overwrites a non-empty one, including one the user cleared, edited, or a prior prefill), and only for `cveId` saves — a pasted-vector save stays empty.
- A non-empty client-supplied `description` at save time wins over both the matched row's existing value and the NVD prefill above (`COALESCE(?, description)` on the update path, a direct value on insert); empty/absent changes nothing about the behavior described above.
- `GET /api/vulnerabilities` accepts an optional `q` query parameter — a case-insensitive substring search over `label`, `cve_id`, `vector`, `description`, and the raw cached `nvd_json` text (the last is what makes the NVD description, affected-product CPE strings, and reference URLs/tags searchable with no schema change or extraction pass), implemented as a five-column `LIKE ... OR` chain with `%`/`_` escaped (`ESCAPE '\'`) so they match literally rather than as SQL wildcards. Still only returns `saved = 1` rows; absent/blank `q` returns everything.

## Frontend

`web/src/` — `App.tsx` does simple state-based view switching (`environments` / `environment-edit` / `interview` / `score` / `vulnerabilities`), no router library. `pages/` holds the five screens, `components/` the shared pieces (`SeverityPill`, `AnimatedScore`, `ScoreChanges`, `EnvironmentResultRow`, `ScoreResult`, `NvdVectorPicker`, `Icon`, `Modal`, `ThemeToggle`, `MarkdownContent`, `MoreExpander`, `WarningBanner`, `CveDetailsView`). `api.ts` wraps every `/api/*` call; `types.ts` mirrors the server's response shapes.

- `ScoreResult.tsx` (extracted from what used to be inline in `ScorePage.tsx`) renders the base-score-card + per-environment result list, and optionally an inline-expand "Save" action (`onSave` prop) that POSTs to `/api/vulnerabilities`. Omitting `onSave` hides the control — used when viewing an already-saved item from `SavedVulnerabilitiesPage.tsx`. Its optional `overwriteLabel` prop shows an italic note in the save panel when the save will update an existing entry rather than create one. See "Scoring page" below for the optional `defaultDescription` and `onClear` props.
- `web/src/lib/severity.ts` — `nvdSeverityToAppSeverity(raw, baseScore)` maps NVD's upper-case `baseSeverity` strings (or the score-band fallback when NVD omits one) onto the app's title-case `Severity` union; also reused to score-derive a severity pill for the saved-vulnerabilities list and its severity filter, which don't carry `baseSeverity` at all.

The results screen's signature interaction: each environment's score animates from the base score to its modified score on load (`AnimatedScore`), with color morphing through the severity scale in transit — the "a 10 might actually be a zero" moment, dramatized once. Respects `prefers-reduced-motion`. `None` severity deliberately renders with no color at all (quiet muted text, no pill) rather than a fifth hue — see "Frontend design" below for why. The severity pill next to the animated number derives its severity from the same live (in-transit) value as the number's color, not the final value — both must land together when the animation settles, or the pill spoils the reveal by snapping to its end state early.

Each changed-metric line in the "why" panel (`ScoreChanges.tsx`) shows a colored ▲/▼/– glyph plus a real signed score number (e.g. `-1.3`, `±0.0`) sourced from the server's `ScoreChange.impact`/`direction` fields, plus a closing "Total:" line and a small order-dependency caveat. Exact per-metric numeric attribution isn't inherently well-defined for CVSS (the formula isn't additive), so `impact` is a **sequential/waterfall** figure: `applyEnvironment()` applies each change one at a time and measures the score movement at each step, which means the per-line numbers always telescope exactly to the row's total delta (reassuring when a user asks "how did three items add up to +1.6?") even though the *split* between two interacting changes could differ if the application order changed. `direction` is simply derived from `impact`'s sign (`worse`/`better`/`neutral`), not a separate ordinal judgment. The "Total:" line gets a `why-total-worse`/`why-total-better` class (bold, `--severity-critical-text`/`--severity-low-text`) derived from the total's sign; zero stays neutral. The severity pill (in both `AnimatedScore` and the base-score-card) sits in a fixed-width `.severity-slot` sized to the longest severity word ("CRITICAL") so score figures stay aligned in a column down a result list regardless of which severity word appears per row — `.pill-none`'s chrome-less rendering still fits the same slot.

`EnvironmentResultRow.tsx`'s collapsed summary renders a red warning-triangle icon immediately before the animated score figure whenever `result.delta > 0`, sized to the score figure's line height (`--text-2xl`) via `.more-vulnerable-icon` — this needs to be announced to screen readers, unlike every other decorative icon use in the app, so `Icon.tsx`'s optional `aria-label` prop flips the SVG from `aria-hidden` to `role="img"` + a `<title>` when set. Its expanded detail panel also renders a `.more-vulnerable-warning` callout (a thin spacing modifier on the shared `.callout-warning` base class — a red-accented card + `Icon name="warning"`, backed by a `--warning-wash` token, a translucent tint of `--action-red-text`) whenever `result.delta > 0`, stating plainly that the environment is more exposed than the base score suggests. `.callout-warning` is also what backs `WarningBanner.tsx`, used by the Scoring page's CVE-lookup and Major-CVEs-fetch errors — one visual language for "something's wrong, here's why" everywhere in the app. Because both the Scoring-page results and the saved-vulnerability detail view render through the same `EnvironmentResultRow`, one implementation covers the more-vulnerable warning in both places.

### Design system

Lives in `web/src/styles.css` as CSS custom properties (no framework): IBM Plex Mono for headlines/scores/vector strings, Archivo for body copy (via `@fontsource/*`, self-hosted — **never** load fonts from a CDN, the app must work fully offline). Import only the `latin-*.css` subset files from `@fontsource` packages, not the bare weight files — the latter pull in every unicode subset (cyrillic, vietnamese, greek, ...) and roughly quadruple the font payload for no reason in an English-only UI.

- `web/src/lib/markdown.ts` — `renderMarkdown(source)` runs `marked` (GFM, `breaks: true`) then sanitizes the output HTML through `dompurify` (an `afterSanitizeAttributes` hook forces `target="_blank"`/`rel="noopener noreferrer"` on every link; `<style>` is additionally forbidden). This is the only place raw description text becomes HTML — descriptions are stored as-is server-side (plain `TEXT` columns, no server-side sanitization) and sanitized only at render time, so raw markdown source round-trips intact through edit forms. `MarkdownContent.tsx` wraps it in a `<div className="markdown">` via `dangerouslySetInnerHTML` — the only `dangerouslySetInnerHTML` call in the app, safe specifically because it always goes through the sanitizer first. Wired up in `EnvironmentsPage.tsx`'s list rows, `EnvironmentEditPage.tsx`'s detail view (edited as a plain `.textarea`, never a WYSIWYG editor, consistent with the rest of the app's plain-CSS design), and the Saved-vulnerabilities list. `web/src/lib/markdown.test.ts` is the mandated safety test (Vitest + `jsdom`, see `web/vitest.config.ts`) — covers basic formatting, forced link attributes, and stripping of `<script>`, inline event-handler attributes, `javascript:` URIs, and `<style>`.
- `Icon.tsx` — a single component (`name` prop) rendering bundled inline SVGs (`trash`, `pencil`, `sun`, `moon`, `chevron`, `question`, `warning`, `external-link`, `eye`, `eye-off`), no icon font/CDN. Icon-only buttons always carry `aria-label`.
- Semantic action colors are tokens in `styles.css`, deliberately distinct hues from the severity palette (which stays reserved, never reused for non-data purposes) — `--action-green`/`--action-yellow` (solid fills, near-black `--action-ink` text on top) and `--action-red-text` (theme-varying outline/icon color, same pattern as `--severity-*-text`). Contrast-validated in both themes via the dataviz skill's `validate_palette.js` `contrast()` export against the real `--surface`/`--surface-card` values — e.g. `--action-green` clears 4.76:1 (light) / 8.36:1 (dark) with black text, `--action-red-text` clears 5.03:1 (light) / 5.83:1 (dark). `--accent` itself clears 4.5:1+ as border/text against both surfaces in both themes (6.32–6.75:1).
- Button classes: `.button`/`.badge` use an accent-outline pattern (`--accent` border + text, transparent background, `--accent-wash` hover fill for `.button`). `.button-primary` uses theme-inversion tokens (`--button-contrast-bg`/`--button-contrast-ink`, theme-scoped) rather than a flat `--accent` fill. `.button-save` (solid green, "Save", never an icon) and `.button-cancel` (solid yellow, "Cancel", never an icon) share `.button`'s size system. `.button-quiet`, `.link-button`, and `.icon-button-quiet` deliberately stay neutral — semantic colors are reserved for Save/Cancel/Delete/primary actions, not a general recolor. `.icon-button` is a fixed-size (2.25rem) square icon-only control; `.icon-button-delete` (red outline + `Icon name="trash"`) and `.icon-button-edit` (accent outline + `Icon name="pencil"`, same box model as delete just in the `--accent` family — an earlier solid-yellow treatment read as a glaring square dominating every row, so it moved to this quieter outline) are its semantic variants.
- Active tabs (`.tab.is-active`) render a solid `--accent` fill + `--accent-ink` text in both themes (a deliberate exception to `.button-primary`'s theme-inversion rule, scoped to tabs specifically). **Gotcha**: `.tab:hover:not(:disabled)` (specificity 0,3,0) must be scoped to `:not(.is-active)`, or it beats `.tab.is-active` (0,2,0) and silently flips the active tab's hover text to the same color as its background (invisible) — caught via Playwright + `getComputedStyle`, not visually (a static screenshot of the non-hovered state looked fine); a hover-state screenshot or computed-style check is needed to catch this class of bug, a plain screenshot isn't enough.
- `Modal.tsx` exports `Modal` (generic dialog: blurred backdrop via `backdrop-filter`, `role="dialog"`/`aria-modal`, focus-trapped, closes on Escape or backdrop click, restores focus to the trigger on close, takes an optional `className`) and `ConfirmModal` (the delete-confirmation specialization — yellow Cancel / red-outline-text "Delete"). Neither list page uses `window.confirm()`.
- Theming: `web/src/lib/theme.ts` reads/writes `localStorage` (`localscore-theme`) and toggles a `data-theme="light"|"dark"` attribute on `<html>`. `main.tsx` applies the preferred theme (stored value, else `prefers-color-scheme`) *before* the first React render to avoid a flash of the wrong theme. `styles.css` defines dark tokens three times by design — behind `@media (prefers-color-scheme: dark)` (pre-JS default), and behind `:root[data-theme="dark"]`/`:root[data-theme="light"]` (both higher-specificity than a bare `:root`, so the in-app toggle always wins over system preference) — keep all three in sync when editing dark-mode tokens. `ThemeToggle.tsx` renders a real `<button role="switch" aria-checked>` (`.theme-switch`) — a pill track with a sliding thumb, light = off (thumb left, neutral `--surface-sunken` track), dark = on (thumb right, `--accent`-filled track), sitting at the far right of the header (`.nav` has `margin-right: auto` to push it there); the active icon rides inside the thumb at 18px and shows the icon for the *action* (moon while light, sun while dark), not the current state.
- `html { overflow-y: scroll; }` reserves scrollbar space unconditionally, so navigating between a short page (e.g. an empty Saved list) and a long one no longer shifts centered content horizontally.
- Severity pill ink is theme-scoped (`--severity-ink`: `#ffffff` light, `#0b0b0b` dark) with the fill hues (`--severity-low/medium/high/critical`) deepened per-theme to keep white text readable on the light-theme fills (each cleared to ≥4.5:1 against white via the dataviz `contrast()` procedure). Foreground *text* uses the separate `--severity-*-text` tokens, not the raw fill hues, wherever severity color appears as text-on-surface rather than fill-with-text-on-top (`AnimatedScore.tsx`'s score-number color, `ScoreChanges.tsx`'s deltas, the outline `SeverityPill` variant) — the fill and text-on-surface contrast pairings are different (e.g. `--severity-medium` measures only ~1.8:1 as raw text against the light surface), and the fill tokens were only ever validated for fill-with-near-black-text.
- `SeverityPill` takes an optional `variant?: "solid" | "outline"` (default `"solid"`); the Saved-vulnerabilities list and the filter-chip severity legend use `"outline"` (border + text colored by severity, transparent fill) since a solid pill there would carry the same visual weight as neighboring neutral `.badge` tags.
- `.badge`/`.badge-severity` share one box model (shape/size/weight), differing only in color. The "ready" badge (`.badge.is-complete`) uses the outline tag pattern with a dedicated `--action-green-text` token, kept separate from the reserved severity palette.
- `QuestionHelpModal.tsx` (interview question help): a circled `?` `icon-button-quiet` next to the question title opens the shared `Modal` with `whyWeAsk` → `helpDetail` (2–4 sentences per question) → `finePrint`, in that order. `Modal`'s `modal-fixed-height` class gives `.modal-body` a `min-height` sized to the largest of the 12 questions' content so the dialog doesn't visibly resize between questions; `.modal-header h2` uses the body font/weight 700 (scoped to modals only — page headings elsewhere keep IBM Plex Mono). `helpOpen` state resets on question change so switching questions via the progress ticks doesn't leave a stale modal open for the wrong question.

### Environments page

- `EnvironmentsPage.tsx`'s page description targets a non-technical reader and includes a `MoreExpander` (a thin `<details>`/`<summary>` wrapper, also reused for the Scoring page's "More") explaining the base-score-vs-environmental-metrics distinction. The create form collects name, an optional description (`.textarea`), and an optional `location` (`.input`); `.new-environment-form` has `gap: var(--space-5)` so fields don't touch.
- `EnvironmentEditPage.tsx` is the dedicated edit view: rename (`.input`), description (`.textarea`, markdown-rendered elsewhere), location (`.input`), a red-outline trash `icon-button-delete` (guarded by `ConfirmModal`), and green `.button-save`/yellow `.button-cancel` calling `updateEnvironment()` (`api.ts`) against `PUT /api/environments/:id`. A second card surfaces "Answer interview" / "Re-answer interview" (labeled by `interviewCompletion["3.1"]`) to reach the wizard.
- `EnvironmentsPage.tsx`'s list-row action: once `interviewCompletion["3.1"]` is true the row shows the accent-outline pencil `icon-button-edit`; until then it shows a text "Answer interview" button. Both open `EnvironmentEditPage`, never the interview wizard directly (the Create form's "Create & start interview" still jumps straight into the wizard on creation, since there's nothing to edit yet).
- `InterviewPage.tsx` has no "Save & exit" control — a plain `.link-button` "← Back to environment" sits above the `<h1>` instead; answers still auto-save per-answer. `App.tsx` routes the interview's `onDone` (both the back-link and the final "Done" button) back to `EnvironmentEditPage` for that environment, not the full environments list.
- **Location field**: migration `0004_environments_location.sql` adds `environments.location TEXT NOT NULL DEFAULT ''` — a short, optional, single-line, plain-text place label ("us-east-1", "Building 4, rack 12"), deliberately not markdown and not involved in scoring/derivation/the interview. `POST`/`PUT /api/environments` accept an optional `location` (COALESCE-on-missing-field pattern), trimmed server-side; a non-empty location renders as a small muted `.environment-location` line directly under the environment name, above the markdown description.
- **Quote stripping**: `server/src/lib/strings.ts`'s `stripWrappingQuotes()` removes one matched pair of wrapping quotes (straight or curly, double or single) after trimming, repeating until no wrapping pair remains, so `"'My Lab'"` fully unwraps to `My Lab`. Applied to `name` and `location` on both `POST /api/environments` and `PUT /api/environments/:id` (not `description` — markdown legitimately uses quotes). A name that becomes empty after stripping still 400s. The create/edit forms' placeholders don't model quoted examples (`e.g. My Data Center`, not `e.g. "My Data Center"`) since that's what taught users to type them in the first place; the server-side strip is the backstop for API callers and anyone who quotes anyway.
- **Two-tier risk-warning system**: an environment can be flagged two independent ways, both surfaced as a red `Icon name="warning"` in the row's badge row on `EnvironmentsPage.tsx` (not itself interactive — Edit is the path to the explanation) and explained in a `.callout-warning` on `EnvironmentEditPage.tsx`.
  - **Tier 1 — `raisesScores`** (`server/src/scoring/raising.ts`): a per-CVSS-version boolean computed from metric+value pairs (not question IDs, so catalog evolution keeps working). Current trigger set: `4.0` flags `MSC/MSI/MSA = H` (Q8 stepping-stone) and `MSI`/`MSA` = `S` (Q9 safety=yes); `3.1` flags `MS = C` (Q8). Only `override` effects are ever checked (`cap` never raises severity by definition). An earlier version of this rule also flagged `CR/IR/AR = H` (Q5/Q6/Q7 "Catastrophic"), but that over-triggered — an environment that legitimately has a lot to lose (e.g. a government IL6 system) was flagged permanently, making the flag meaningless exactly where stakes are highest — so `CR`/`IR`/`AR` were dropped from the trigger set. `computeRaisesScores()` returns the per-version booleans; `computeRaisingAnswers()` returns deduplicated `{ questionId, optionId }` provenance.
  - **Tier 2 — `redFlags`** (`server/src/scoring/redflags.ts`): computed straight from `environment_answers` (not derived metrics, since Q10–Q12's supplemental answers never produce a metric), deliberately catalog-coupled (conditions reference `questionId`/`optionId` pairs directly, defended by a catalog-integrity test asserting every referenced answer — exported as `REFERENCED_ANSWERS` — exists in the shipped catalog). "High stakes" = any of Q5/Q6/Q7 "Catastrophic" or Q9 safety "yes"; every rule pairs a stakes condition with a readiness gap so a flag never fires on stakes alone: `uncertain_recovery` (high stakes + Q10 "Uncertain"), `concentrated_availability` (Q7 "immediate" + Q11 "concentrated"), `hard_to_patch` (high stakes + Q12 "Hard"). Skipped/unanswered questions never satisfy a condition.
  - `GET /api/environments` (list) returns `raisesScores: { "4.0": boolean, "3.1": boolean }` and `redFlags: string[]` (ids). `GET /api/environments/:id` (detail) additionally returns `raisingAnswers` and `redFlags: { id, answers[] }[]`, using the same deduplicated-provenance shape. Both are computed at request time from `environment_answers` rather than the persisted `environment_metrics` cache, since only the live derivation carries questionId/optionId provenance. An environment with no answers reports `false`/`false` and empty arrays.
  - `EnvironmentEditPage.tsx` fetches the catalog to translate provenance into plain English and renders up to two `.callout-section` blocks (score-raising, then red flags) inside the `.callout-warning`, separated by a hairline divider only when both are present; either renders alone when only one tier triggers, and the callout disappears entirely when neither does. Each red flag renders its plain-English meaning (`RED_FLAG_COPY`) followed by its responsible question/answer pairs.
  - **Callout readability**: each `.callout-section`'s title/explanatory paragraph is grouped in its own `.callout-section-intro` div, visually distinct from the indented (`padding-left: var(--space-4)`) `.raises-scores-list` that follows. Each list item renders as two lines: a bold `Q:` prefix + question text, then a normal-weight `A:` prefix + answer text — a scoped `.raises-scores-list li p + p { margin-top: 0; }` override keeps that pair tight while the general `.callout-section p + p` rule gives wider spacing (`var(--space-3)`) between successive pairs, and an even wider gap (`var(--space-5)`) separates each section/red-flag block's own intro. Both the score-raising section and every red-flag block share the one `.raises-scores-list` class.

### Saved vulnerabilities page

- `SavedVulnerabilitiesPage.tsx` mirrors `EnvironmentsPage.tsx`'s list/empty-state/delete structure, with inline expand-to-view-and-rescore per row via `ScoreResult`. Each `<li>` is one `.card.vulnerability-row` containing both the clickable header and the conditionally-rendered detail panel (reuses `.result-row-detail`'s divider treatment) — not a header card with a separate unstyled sibling — so the expanded content stays visibly bounded within its own card. Clicking anywhere on the header toggles expand/collapse; the View/Hide, Edit, and Delete buttons inside it call `event.stopPropagation()` so they don't also re-trigger the row's own toggle. `vulnerabilities.description` renders via `MarkdownContent`, same as the environments list.
- The accent-outline pencil `icon-button-edit` per row (next to View/Delete) swaps the row's header for an inline edit form (`.environment-edit-form`, wrapped in `.vulnerability-row-edit` to restore the `var(--space-5)` padding that the view-mode layout otherwise sets to `0`) with label/description fields and green `.button-save`/yellow `.button-cancel`, calling `updateVulnerability()`. No separate edit page — the row itself becomes the form, then reverts to the normal header on save/cancel.
- The View/Hide button is a neutral 2.25rem `.icon-button-quiet` with `eye`/`eye-off` icons (view/hide isn't one of the reserved semantic actions), and stays in place (no "Loading…" label swap) while the detail fetch is in flight.
- `.vulnerability-row-header .environment-name` gets `overflow-wrap: anywhere` so a pasted-vector save's default vector-string label (150+ chars, unbroken) wraps inside the card instead of overflowing; `.environment-row-main` has `min-width: 0`. The badge for a pasted-vector save reads "Vector" (not "Pasted vector") — kept short to match "NVD".
- **Action cluster** (`.environment-row-actions`, the eye/edit/delete cluster): `.vulnerability-row-header` uses `align-items: flex-end` + `flex-wrap: nowrap` at desktop, so the cluster anchors to the header's bottom-right and tracks the bottom edge of however tall the text column gets; a `@media (max-width: 480px)` override restores `flex-wrap: wrap` for a deliberate stacked layout at that width. `.environment-row-actions` keeps `flex-shrink: 0`.
- **CVE details disclosure** (`CveDetailsView.tsx`, shared with the Scoring page — see below): `.cve-details-summary` is its own bounded row (`border` + `border-radius: var(--radius-md)` + `background: var(--surface-sunken)`, darkening to `--surface-card` on hover) with a rotating chevron (`size={20}`), collapsed by default, expanding on click to reveal description/dates/affected-products/references. Inside the expanded body, affected-product chips and reference tags are recolored to `--ink-secondary` (not the app's usual accent-outline `.badge`, and not `--ink-muted`, which fails contrast at this size) so the hierarchy reads link = accent = interactive, chip = neutral = metadata. A plain external NVD link (`Icon name="external-link"`, `target="_blank" rel="noopener noreferrer"`) renders in a `.cve-details-footer` (`display: flex; justify-content: flex-end`) as the body's last element when `cveId` is present — inside the expanded body rather than the summary button, so it needs no `stopPropagation` (nesting an `<a>` inside the summary `<button>` would be invalid HTML/ARIA). `CveDetailsView` takes an optional `showDescription` prop (default `true`, so the Scoring page's fresh-lookup flow is unaffected). The Saved page passes `showDescription={!vuln.description}` for its expanded row, since an NVD-sourced saved row already shows its own `description` field in the row header — avoids showing the NVD description twice, while still surfacing it inside the details disclosure if the user has cleared the row's own description.
- **Filter/search control bar** (`.filter-bar`, between the page header and the list): Type (`All`/`NVD`/`Vector`, single-select) and Severity (`All`/`Critical`/`High`/`Medium`/`Low`, multi-select) chip groups, plus a debounced (280ms) search `.input` that spans the full row width (its own row via `flex-basis: 100%`, not shrink-wrapped). Filter options are a `.filter-chip` pill control sharing the app's accent-outline-to-solid-accent-fill "selected" convention (same pattern as `.tab.is-active`/`.badge.is-complete`) rather than reusing `.tabs` (reserved for page-level mode switching) or a plain `.badge`. Severity chips double as a color legend, using the same `--severity-*-text` (outline, unselected) and `--severity-*`/`--severity-ink` (solid fill, selected) tokens validated elsewhere — a deliberate, narrow reuse of the severity palette for an actual severity control.
  - **Type** stays single-select (`TypeFilter` string state), since its options are mutually exclusive by construction. **Severity** is a `Set<SeverityFilter>` (`severitySet`): clicking a severity chip toggles membership, multiple can be active at once, and "All" represents the empty set (clicking it clears the set; there is deliberately no way to distinguish "all four selected" from "All" in the UI). Filtering passes when the set is empty or the row's severity is a member. Both are client-side `useMemo` filters over the already-fetched list. Severity matching reuses `nvdSeverityToAppSeverity("", vuln.baseScore)` — the exact function the row's own `SeverityPill` calls — so a row can never filter into a bucket different from what it visibly shows; `None`-scored rows (a 0.0) have no severity chip and only appear when the set is empty.

Existing no-arg callers (`ScorePage.tsx`'s overwrite-detection fetch) are untouched.

A viewed/expanded row that stops matching simply isn't rendered by the filtered map — sufficient to "collapse" it, no separate state reset needed.

### Scoring page

- `ScorePage.tsx` is built around three real tabs (`role="tablist"`/`tab`/`tabpanel`, `.tabs-shell`/`.tabs`/`.tab`) in order: **Look up a CVE** (default), **Paste a Vector**, **Major CVEs**. Each panel opens with a `.tab-purpose` line stating what that tab is for. The page description targets a non-technical reader and has a `MoreExpander` with plain external links to NVD's and MITRE's CVE search (no network call from the app itself, just `<a href>`s).
- **Offline detection**: `web/src/lib/online.ts`'s `useOnlineStatus()` hook wraps `navigator.onLine` plus `online`/`offline` window event listeners, returning a setter too — a CVE lookup that fails with a `502` (NVD unreachable) also flips it false, since `navigator.onLine` is unreliable on some platforms/only reflects the network interface, not actual internet reachability. The "Look up a CVE" tab gets `disabled` + an explanatory tooltip whenever offline; "Major CVEs" gets the same treatment only when it *also* has no cached data to fall back on (checked client-side against the already-fetched `MajorCvesResponse`). An effect auto-switches away from either tab to "Paste a Vector" if the user goes offline while on them.
- **CVE lookup errors**: `WarningBanner.tsx` renders any `cveError` as a red-accented `.callout-warning` card with a warning icon instead of bare error text. Only a `502` (unreachable) redirects to the paste tab — a `404` (not found) or `422` (no CVSS data) stays on the CVE tab with the banner explaining why, since those aren't connectivity problems. Both this banner and the Major CVEs tab's fetch-error banner span the full panel width (`.tab-panel .callout-warning { width: 100%; }` — the root cause was `.score-form`'s `align-items: flex-start` shrink-wrapping children to their text width).
- **Major CVEs tab**: fetched via `getMajorCves()` on mount and rendered as a plain list (`.major-cve-row`) of ID (`--text-lg`, so it reads as the row's primary identifier) + outline `SeverityPill` + score + published date — only the ID and score figure stay mono, the date/prose use the body font. A `"Last updated <timestamp>"` / `"Updated just now"` line reflects the response's `cached`/`fetchedAt`. Clicking a row calls the same `performCveLookup()` used by manual CVE-ID entry and switches to the CVE tab. Each row also renders a plain external NVD link with its own `stopPropagation` (split into a `<button className="major-cve-row-lookup">` plus a sibling `<a>`, since nested interactive elements aren't valid HTML/ARIA).
- **Overwrite messaging**: `ScorePage.tsx` fetches `listVulnerabilities()` on mount (refreshed again after every successful save) and locally matches the current result against that list — by `cveId` for a CVE-sourced lookup, by `result.base.vector` for a pasted vector — to compute an `overwriteLabel` passed into `ScoreResult`'s save panel. This has to be known *before* the save call resolves (the server's `overwritten` response flag alone is too late), so it's derived from client-side state that mirrors what the upsert will match against.
- **Save-time description**: `ScoreResult.tsx`'s save panel has a description `.textarea` below the label input ("Markdown supported" copy, matching the Saved-page edit form); `onSave`'s signature carries a second `description` argument. `SavedVulnerabilitiesPage.tsx` doesn't pass `onSave` to `ScoreResult`, so it's unaffected. `ScoreResult` also takes an optional `defaultDescription` prop (mirroring `defaultSaveLabel`) to prefill the textarea; `ScorePage.tsx` passes the NVD description (`cveLookup.details.description`) only when the result is CVE-sourced (`lookupSource` is set), leaving a pasted-vector result's textarea empty since there's no NVD description behind it. Known asymmetry, documented inline rather than fixed: if a user clears this prefill and saves, the server's existing "prefill only when empty" rule (see "NVD lookup & saved vulnerabilities" above) will re-add the NVD description to the stored row on a fresh save. The save panel's input/textarea span the full card width (`.save-form` carries no width clamp); only the field widths changed, the shared Save/Cancel buttons (also used by the Saved page's inline edit form) keep their natural width.
- **Clear-result control**: `ScoreResult` takes an optional `onClear` prop; when present, a red-outline `icon-button-delete` trash button (`aria-label="Clear this result"`) renders at the far right of the save-panel's collapsed row, next to the Save button/Saved confirmation (hidden while the save form itself is open). `ScorePage.tsx` wires it to clear `result`, `lookupSource`, and `error` only, leaving the CVE lookup data and vector textarea untouched so re-scoring works immediately. No confirmation dialog, since clearing is non-destructive (the result can be recomputed). `SavedVulnerabilitiesPage.tsx` doesn't pass `onClear`, so its expanded row shows no clear control (the existing view/hide toggle already serves that purpose there).
- **Stale-result invariant**: a rendered result is only valid for the exact input that produced it. `ScorePage.tsx` clears `result` (and `lookupSource`) at the top of `performCveLookup()` (covers the lookup form, a Major-CVE row click, and Refresh alike, including a same-CVE refresh since NVD data can change between fetches), in the vector textarea's `onChange`, and in the NVD vector picker's `onSelect`. Each clearing site carries a comment noting this is an invariant, not a one-off patch, so a future input source inherits it deliberately. Failed scoring already clears the result.
- **Focus symmetry**: one effect keyed on `mode` focuses `cveInputRef` (`#cve-input`) when `mode === "cve"` (including on the initial render, since "Look up a CVE" is the default tab) and `vectorInputRef` when `mode === "paste"`. The Major CVEs tab has no input. The offline-redirect effect still runs first when applicable, so the focus effect only ever tries to focus a tab that's actually showing.
- **CVE details**: `CveDetailsView.tsx` is the one shared rendering component for both this page's fresh-lookup flow and the Saved page's expanded-row detail view (see "NVD lookup & saved vulnerabilities" above for `extractCveDetails()`). The description has no length clamp — the collapsed-by-default disclosure (see "Saved vulnerabilities page" above) is what bounds the page now, not an inner "Show More" toggle.
- **`.option-list` spacing**: the shared `.option-list` class (rendered by both `InterviewPage.tsx`'s question card and `NvdVectorPicker.tsx`) carries no top margin of its own; `.interview-question .option-list` scopes the `var(--space-5)` top margin to the interview specifically. `NvdVectorPicker`'s other two homes (this page's CVE-lookup result and the Saved page's expanded-row detail) already space their own children via a flex `gap` (`.cve-lookup-result`'s `var(--space-4)`, `.result-row-detail.stack`'s `var(--space-5)`), so the shared class doubling that spacing was the bug; each context now owns its own spacing directly.
- The signature score-reveal animation, the "why" panel's waterfall attribution, and the more-vulnerable warning are documented once, up front in "Frontend" above, since `ScoreResult`/`EnvironmentResultRow` are shared with the Saved page.

### Copy, branding & Title Case conventions

- Every user-facing "localscore" mention is wrapped in `<strong>`.
- No em-dashes anywhere user-facing — not in `web/src/` copy, not in `server/src/catalog/catalog.ts` (question/label/`whyWeAsk`/`finePrint`/`helpDetail`), not in user-facing server error strings (`server/src/scoring/parse.ts`, `server/src/lib/nvd.ts`, `server/src/routes/cve.ts`). `server/test/catalog.test.ts` has a regression test scanning every catalog string field for `—`.
- Button/tab/`.link-button` labels use Title Case. Option cards, `aria-label`s, tooltips, and placeholders stay in sentence case.

### Frontend design

When designing or building UI in `web/` — new screens, layout/visual changes, or anything touching typography/color/spacing — invoke the `frontend-design` skill first, before writing JSX/CSS, so the interview and results screens read as intentionally designed rather than default scaffolding.

For any color tied to *data* specifically — severity/status colors, deltas, chart series, stat tiles — also invoke the `dataviz` skill and run its `validate_palette.js` against candidate hexes rather than picking colors by eye. This is how the current severity palette (`--severity-low/medium/high/critical` in `web/src/styles.css`) was derived: the skill's reserved status palette (good/warning/serious/critical), contrast-checked with near-black text on every fill. `None` deliberately has no color at all (quiet muted text) — a content-driven choice, not an oversight, so don't "fix" it by giving it a hue.

### Verifying frontend changes

This environment has no built-in browser/screenshot tool, but a system Chrome install is available at `/Applications/Google Chrome.app`. To actually see and click through UI changes rather than trusting the code: `npm install --no-save playwright-core` (ad-hoc — do **not** add it to any `package.json`, it's a verification tool, not an app dependency), then drive it with `chromium.launch({ executablePath: "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome", headless: true })`. Screenshot with `page.screenshot({ path, fullPage: true })`.

Pitfall hit while building the interview UI: Playwright's `text=` selector does a case-insensitive substring match, so `page.click("text=Next")` can silently click a non-interactive element whose text happens to contain "next" (e.g. an option description like "...wiped on the **next** automated rebuild") instead of the actual Next button — no error, just a no-op. Use `page.getByRole("button", { name, exact: true })` or scope with a specific CSS class (e.g. `.interview-nav .button-primary`) instead of loose text matching.

## Development

### Commands

Run from the repo root unless noted.

- `npm install` — installs all workspaces.
- `npm run dev:server` — server on :8080 with reload (`tsx watch`).
- `npm run dev:web` — Vite dev server with `/api` proxied to :8080 (run alongside `dev:server`).
- `npm run build` — builds `web` (static assets to `web/dist`) then `server` (to `server/dist`, migrations copied alongside).
- `npm start` — runs the built server (`server/dist/index.js`); serves the built frontend + API on one port.
- `npm test` — runs the server's Vitest suite (`server/test/*.test.ts`) then the web's (`web/src/**/*.test.ts`). To run one file: `npm run test --workspace server -- test/catalog.test.ts` (or `--workspace web`).
- `npm run typecheck` / `npm run lint` — both workspaces. CI runs all four (`lint`, `typecheck`, `test`, `build`) on every PR and push to `main`.
- `podman build --format docker -t localscore .` then `podman run ...` — container build. The maintainer uses **Podman, not Docker**; the Dockerfile/compose.yaml are plain OCI and must keep working under Docker too, but write any documentation/examples with `podman`. **`--format docker` is required for a direct `podman build`** — Podman's default OCI build format silently drops the Dockerfile's `HEALTHCHECK` instruction with just a warning, no error.
- `podman compose up` — builds and runs via `compose.yaml`. Verified this does **not** need `--format docker`: going through the external `docker-compose` provider already produces a Docker-format image with `HEALTHCHECK` intact (confirmed by `podman inspect` reporting `healthy`). So the flag only matters for a bare `podman build`, not for compose.
- Published image: `docker.io/eengelking/localscore` (tags `latest`, `1.0.4`) — pushed with `podman push`. See "Publishing a release image" below for the required tag/push/verify procedure — never push an untagged or `latest`-only build.

Verified end-to-end: both `podman build --format docker` + `podman run`, and `podman compose up`, produce a container `podman inspect` reports as `healthy`, with the API/frontend reachable and a full create-environment round trip working.

`DATA_DIR` (default `./data`) and `PORT` (default `8080`) are read from the environment; see `.env.example`.

### Testing during development vs. before merge

Two distinct testing procedures — don't conflate them:

- **Test 2 (npm, during development)** — the default while iterating. Build and run the built server directly on port 8081 (`PORT=8081`), not the Vite dev server: `npm run build && PORT=8081 node server/dist/index.js`. This matches how the container actually runs (one process, built frontend + API) without the overhead of a full container build on every check. **Always stop the process cleanly when done** (kill it — don't leave it running in the background between tasks). Use this for functional checks, API round trips, and UI verification via Playwright (see "Verifying frontend changes" above) throughout the work.
- **Test 1 (container, last step before merge)** — the final gate confirming the container builds and runs as it will in production, on port 8080. Container name `localscore-test`, image tag `localscore:local`. Before building: check whether a container named `localscore-test` (or anything else) is already bound to port 8080 — if so, **ask the user before taking it down**, don't stop it unilaterally. Always build a fresh image (don't reuse a stale one) — `podman build --format docker -t localscore:local .` — then `podman run --name localscore-test -p 8080:8080 ...` and confirm `/api/health` reports healthy and the frontend loads. Clean up afterward per "Container testing cleanup" below (ask before removing).

## Releasing

### Publishing a release image

This is separate from Test 1 (which only builds `localscore:local` for local verification and is never pushed). A release build is any container image meant to be published to `docker.io/eengelking/localscore`.

Since 1.0.0, this procedure runs **after every PR merge to `main`**, by default — not just when the user explicitly asks for a release. Once you've confirmed a PR is merged, treat cutting the release as the next step of finishing that work.

1. **Decide the version bump.** Current version lives in the root `package.json` (`server/package.json` and `web/package.json` are kept in sync with it — bump all three together). Default to a **patch bump** for fixes/small changes and a **minor bump** for new features, from the prior published tag (e.g. `1.0.0` → `1.0.1` or `1.1.0`). Only bump the **major** version when the user has explicitly said this is a major/breaking release — never infer "major" on your own from the diff size. If it's ambiguous whether a change is patch- or minor-sized, ask the user rather than guessing.
2. **Update the version** in `package.json`, `server/package.json`, `web/package.json` to the new version number, and update any docs that literally quote the current published tag (README.md's image line, CLAUDE.md's "Published image" line above) so they don't go stale.
3. **Build fresh** — don't reuse a stale local image: `podman build --format docker -t localscore:<new-version> .` (`--format docker` is required for the `HEALTHCHECK` to survive, per the gotcha above).
4. **Tag** the built image for the registry with both the new version and `latest`:
   - `podman tag localscore:<new-version> docker.io/eengelking/localscore:<new-version>`
   - `podman tag localscore:<new-version> docker.io/eengelking/localscore:latest`
5. **Push both tags**:
   - `podman push docker.io/eengelking/localscore:<new-version>`
   - `podman push docker.io/eengelking/localscore:latest`
6. **Verify the push succeeded** — don't just trust a clean exit code from `podman push`. Confirm the new tag is actually live on the registry, e.g. `podman manifest inspect docker.io/eengelking/localscore:<new-version>` (or `skopeo inspect docker://docker.io/eengelking/localscore:<new-version>` if available) and check that `latest` now resolves to the same digest as `<new-version>`.
7. **Tag the release in git too**: `git tag -a <new-version> -m "<new-version>" && git push origin <new-version>`.
8. Clean up the local release build per "Container testing cleanup" below (ask before removing) once the push is verified.

### Container testing cleanup

When you `podman run` a container to manually verify something (health check, a route, a full rebuild), it's a temporary test artifact, not something to leave running or lying around:

- **Ask before deleting.** Once testing is done, tell the user what you're about to remove (container name, volume, image) and get a go-ahead before running `podman rm` / `podman rmi` / `podman volume rm` — don't delete silently, even though it's your own test container.
- **Clean up after yourself.** Stop and remove test containers/volumes when done (after confirmation), and run `podman image prune -f` after repeated `podman build` runs against the same tag — each rebuild orphans the previous image as a dangling `<none>` (this happened during initial Podman verification: 4 dangling images, ~1.5 GB, from 3 build iterations of the same `localscore:local` tag).

## Known gotchas

- **npm workspace hoisting affects the Dockerfile.** `npm ci` hoists shared dependencies to the workspace-root `node_modules`, not `server/node_modules` — the runtime image stage copies `/app/node_modules` (root), not a per-workspace one. If you add a server-only dependency that npm decides *not* to hoist (e.g. a conflicting version), the runtime COPY may need to also grab `server/node_modules` — check after `npm ci` whether it exists before assuming it doesn't.
- **`npm audit` reports 5 vulnerabilities** (3 moderate, 1 high, 1 critical) in the `vite`/`vitest`/`esbuild` dev-tooling chain (dev-server-only exposure, not a runtime/production risk). Fixing requires a breaking major-version bump to `vite`/`vitest` — left as-is; don't be surprised by it, and don't `npm audit fix --force` without deliberately taking that upgrade.
- **`podman compose build`/`up` can fail locally** with `error listing credentials - err: exec: "docker-credential-desktop": executable file not found` if `~/.docker/config.json` has `"credsStore": "desktop"` left over from Docker Desktop, even though Podman is what's actually running. Workaround for a one-off command: `DOCKER_CONFIG=<empty-dir-with-{}-config.json> podman compose ...`. Don't edit the user's real `~/.docker/config.json` to fix this — it's outside the project and outside this repo's concern.
